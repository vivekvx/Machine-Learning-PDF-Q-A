# Hybrid offline PDF assistant: implementation and verification

**Date:** 2026-10-15. **Status:** working **limited local prototype** on this Apple M2 Air, with important citation and generalization limits. The existing `server.py` FastAPI RAG application, QASPER experiments, scratch decoder, frozen pointer checkpoint/tokenizer, previous benchmark files, and sealed sets were not modified. No model was trained or fine-tuned.

**Version note:** The measurements below are the preserved v8 development results. A later v9 source-selection and UX change is described in the [service README](scratch/pdf_qa/README.md). Its revised generation quality on a long user-supplied PDF is **unverified**: the first guarded attempt stopped when swap growth exceeded the 600 MB safety ceiling. No PDF bytes or extracted text from that attempt were saved as research artifacts.

## What runs

The primary interface for this experiment is the existing separate [scratch PDF service](scratch/pdf_qa/app.py) at `http://127.0.0.1:8766/`. Its original `/api/ask` scratch-only pointer route remains available. The new `/api/hybrid/ask` route offers two comparable configurations:

1. **Local Qwen RAG:** reuse `src.pdf_loader` and `src.chunking`, retrieve with the service's local TF-IDF+FAISS index, then use Qwen on bounded, page-labeled source excerpts.
2. **Hybrid Scratch + Qwen RAG:** identical PDF, index, retrieval, excerpts, prompt settings, and Qwen model. A factual question with four genuine, representable source candidates also calls the frozen scratch pointer. Its selected span is labeled as *unverified optional guidance*. Broad questions, missing facts, and unsupported pointer inputs bypass it. The failed evidence checker is never called.

The scratch pointer is an original, randomly initialized and trained **extractive** reader; it is not a general generator. The separate scratch decoder does not yet answer QA reliably. Qwen3-0.6B was pretrained by the Qwen team, and we did not train or fine-tune it. Deterministic retrieval, intent routing, source-offset checking, resource guards, and citation syntax checking are application logic. There is no rule-generated answer fallback.

The HTML interface now accepts a PDF, shows page and chunk counts, lets the user select a mode, keeps an index for repeated questions in the current process, and displays answer status, page-linked exact excerpts, pointer use/bypass reason, section coverage, time, and memory. It rejects damaged or text-empty PDFs with a readable 422 response and says OCR is unavailable. The current limits are 12 MB file size, 120 extracted text pages, and one million extracted characters. Only the local process stores the PDF index in memory; it does not add uploads to a training set.

## Retrieval, prompts, and safety

The deterministic local intent router handles factual lookup, explanation, comparison, section summary, whole-paper summary, and explicit out-of-scope requests. Factual and explanation queries use ranked TF-IDF+FAISS chunks. Whole-paper summaries take section-diverse excerpts from available Abstract, Introduction, Methods, Results, Discussion, Limitations, and Conclusion headings, plus spread samples where needed. At most 12 excerpts are considered. A summary over more than three excerpts first makes source-ID-labeled notes in groups of three, then synthesizes within an **actual tokenizer-counted** 1,024-token context. It keeps all intermediate notes or aborts; the final stage includes as many raw excerpts as fit, and records those IDs. It does not send a 40-page document in one request. A 40+ page real PDF has **not** yet been benchmarked, so full coverage and answer quality there are unverified.

Qwen receives system/user messages using its local chat template with `enable_thinking=False`, greedy batch-1 streaming, `<|im_end|>` EOS checking, 96-token factual, 160-token explanation, 160-token intermediate, and 224-token final-summary caps. Exposed thinking/control tokens are rejected. The worker receives only local file paths, sets Hugging Face offline flags, disables app-controlled telemetry, and monkeypatches socket connection APIs to fail closed. There is no cloud fallback. Repeated questions reload the model in a subprocess: this costs about 0.47–0.60 s model-load time per measured official-model request, but prevents simultaneous Qwen and pointer residency under current memory pressure.

Before loading, the parent verifies the model, tokenizer and license SHA-256, package pins, available RAM ≥1.2 GB, macOS pressure-free ≥20%, and disk ≥1 GB. While running, a quarter-second watchdog aborts below 0.7 GB available, below 10% pressure-free, above 600 MB growth in swap-used or swap-out, above 2.5 GB worker RSS, or after 180 seconds. GPU-heavy requests are serialized. Allocated `swap.free` is observed but not treated as a fixed macOS swap ceiling. Neither macOS-wide GPU memory limits nor swap files were changed.

Every evidence ID is assigned by the application to an excerpt with an exact page-text offset. Unknown/malformed IDs, missing citations, and length-truncated outputs are labeled unverified. The UI shows actual page numbers from PyMuPDF, not generated page guesses. A lexical warning asks for manual checking when cited text has weak word overlap or a paragraph pools several citations. **Valid source IDs and lexical overlap do not prove entailment.** A non-medical filter is not applied to arbitrary user uploads; the user should upload only materials they are permitted to process, and local processing does not imply training or redistribution rights.

## Measured outcomes and limits

The frozen [official-model eight-response exercise](scratch/pdf_qa/hybrid_eval/official_v2/manifest.json) used one **original synthetic** four-page technical PDF, four questions asked in both modes, and the exact preserved fixture bytes. All eight HTTP requests completed. Both modes included the correct value for two explicit facts and abstained on the absent accuracy question through a **deterministic measured-field gate**. The hybrid called the pointer for the two factual questions, selected the correct spans, and did not change answer correctness. The summary in both modes included the problem, method, results, and limitation from four different pages, with four valid IDs pooled at the end; the lack of sentence-specific citation mapping requires review. [Metrics](scratch/pdf_qa/hybrid_eval/official_v2/metrics.json), [row outputs](scratch/pdf_qa/hybrid_eval/official_v2/http_results.jsonl), [offset verification](scratch/pdf_qa/hybrid_eval/official_v2/verification.json), and [assistant content check](scratch/pdf_qa/hybrid_eval/official_v2/ASSISTANT_CONTENT_REVIEW.md) give the details. No independent human accuracy claim follows from these eight responses.

On this M2's 8 GB unified memory, the official-model exercise sampled **806 MB peak MLX allocation**, **661 MB peak worker RSS**, **1.108 GB minimum available system memory**, **27% minimum pressure-free**, **221 MB maximum per-request swap-used growth**, and **4.5 MB maximum swap-out growth**. All were inside the configured limits. The 8 GB system already had several GB of used swap; these are specific safe runs, not a promise of comfortable headroom with other apps. The local server was also exercised through a real in-app browser, including PDF upload, a factual answer, a four-section summary, and expandable source excerpts. Corrupt and text-empty PDFs returned HTTP 422; the HTML and `/api/status` returned 200.

The small real CPython spot check exposed a **wrong citation**: a correct-looking transformation answer cited an excerpt on page 2 while its supporting sentence was on page 1. Another location question abstained despite source text about `Tools/scripts`. Earlier community-conversion development runs also showed uncited answers, output truncation, and invented evidence IDs; the app now marks those conditions unverified, and the official model is pinned separately. These failures are reasons **not** to claim general real-document QA accuracy.

After the final code restart, a second [live HTTP smoke record](scratch/pdf_qa/hybrid_eval/official_live_smoke_v1/manifest.json) confirmed the running official-model service again uploaded the identical four-page PDF and returned a cited `prefix scan` factual answer and a four-section summary. The browser was reloaded, uploaded that PDF through its file control, and displayed both outputs with expandable page excerpts. This was a functional check on the same easy fixture, not an additional independent evaluation.

Final checks: **16/16** scratch PDF/hybrid focused tests and **6/6** existing RAG regression tests passed; Python compile checks passed; the read-only [hash checker](scratch/pdf_qa/hybrid_eval/check_official_hashes.py) verified **13/13** preserved official-run files. The live `/api/status` and HTML both returned HTTP 200 after restart. The browser exposed and then enabled Send at the correct upload state. The server was left running on localhost for user testing. The research files remain local and uncommitted; no production file has a tracked diff.

## Decision

**GO for a supervised localhost demo and further controlled evaluation** on user-supplied, legally processable PDFs. **NO-GO for a claim of robust general research-paper QA, citation factuality, pointer improvement, or from-scratch generative QA.** Next: prepare a diverse, rights-cleared real-PDF benchmark with independent claim-level citation review and a 40+ page stress case; keep Qwen-only as practical default unless paired tests show a pointer benefit.
